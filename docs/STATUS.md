### M13: Composed bind (D112)

One recipe step binds a connected group of tasklets to a chain of unit BRMs
as one accelerator: the links inside are FIFOs, only the outer ports get
streamers, and the cluster file holds one accelerator with one register
window, which is one SNAX shell wrapper. The chains NPBench's kernels
contain: multiply → accumulate (every MatMul), scale → multiply-accumulate
(gesummv, gemm, k2mm), accumulate → add → max (mvt, gemm, mlp), subtract →
exp → accumulate (softmax). Two MatMuls in a row (atax) still chain through
L1, because the first result is reused across rows. The rows replace A2A0–A2A5
(a link between two shell accelerators, parked as open item 53) and are a
first cut, planned in a round of their own.

37. The expression grammar (D68, D77) has `+ - * //` only: a tail tile needs `min` (open item 31), a branch needs comparisons, and jacobi1d's tasklet a cast (`dace.int64(x) // 3`). Extended when a kernel needs it.
38. The DMA moves a container as contiguous 64-byte beats from a beat-aligned base, so a container in L2 and L1 must be contiguous; `memory.align` rejects the rest (D86). Strided or 2D transfers when a kernel needs them (a tail tile, open item 31, or a 2D tile); a check of the DMA's loop count (`dma.dims`) comes with them (D89).

The views work on filtered traces (D49), and the movement index of the N = 4096 run builds in under a second; a more compact trace format is decided when a run needs it.

A decision of its own when built.
44. Reductions over tiles: an accumulator task starts from the op's identity and overwrites its output, so a reduction split by a tile loop needs partial sums per tile and a final combine. Until then no tile loop may sit around a `reduce` memlet (D101); decided with LOW3b.
45. A unit BRM's nest is one-dimensional (D70): `bind`'s order check and the lowering's address check reject a 2-D container, and an operand reused across an outer loop (`x` in `A @ x`). With those checks relaxed in a scratch copy, a row sum, a column sum, `A @ x` and `x @ A` ran to checked runs with `elementwise_mul` and `accumulate`, so the unit BRMs need a dataflow that states beats and lanes and leaves the operand's rank to the memlet. Decided in ND1 (part of open item 1; amends D70 and D73).
46. No transform tags an outer map `temporal` or `tile` without splitting it, and `bind` under an untagged outer map fails with a raw `ExprError` instead of a named error. Decided in ND1.
47. An in-place update (`y += x`) imports and binds but does not lower: the writer's task waits for its own node's reader (`TaskListError`). mvt, gemver, gemm and the stencils need it. Decided in LOW4.
48. The flow sizes a kernel's inputs from one bound symbol only (`kernel_inputs`), and a scenario fill takes 1-D arrays only. Decided in ND1.
49. The engine-alone number C3 compares against (firings times II, plus latency) is computed nowhere; it belongs in `design.md` (DSE0).
50. Model speed. A scratch run gave about 4,000 simulated cycles per second at trace off (`vecadd`, W = 8, 32 banks, 131,072 elements), spread flat over the streamers, the banks and the interconnect, and half of that flow's time was outside the model (sandbox, check, report). So C1 rests on turnaround and cause, not on cycles per second. Options, in order: timing-only runs (TIM1), periodic extrapolation (BLK1), then a compiled core for the platform components behind the same cluster file, checked against the Python model by the byte-identical tests (D21); users would still write only BRMs. BASE2 pins the numbers; the compiled core is parked (D114).

What SNAX has to change for a generated accelerator (D111): a Bender dependency on the bundle, pointed at a local folder through `Bender.local`; a target with a fixed accelerator name listing the files `snaxgen` generates for it; later a file list `snaxgen` writes itself, so a new accelerator name needs no hand-written target. SNAX's wrapper template instantiates `<name>_shell_wrapper`, so the generated wrapper carries that module name. Settled in LNK2.
52. Known differences between SNAX-MODEL and the SNAX cluster on `snax_alu`: SNAX starts all streamers of an accelerator with one CSR write, the model starts each streamer on its own (D36); SNAX loads data on a DMA core of its own behind a barrier, the model has one controller (D37). Both change control overhead only, and both are fixed in the model. Decided in ANC2.
53. A link between two shell accelerators (M13's first form, D101): it amends D12 and D51 and needs a change to the SNAX shell. Parked (D112); the composed bind covers chains inside one accelerator.
54. Sizes and float checks for NPBench's kernels (D113): which kernels take PolyBench's SMALL in a 128 KiB L1 with their transients (gesummv and k3mm do not), and the tolerance of the NumPy comparison for float sums. Decided in FE1a.

What a GVSoC backend would do to the rest (D115): SNAX-MODEL kept as the reference the C++ components are checked against, or retired; the run viewer and the reports, which read the model's profile and trace (D38–D40), fed by a converter or rewritten; the second half of SNAX-LOWER (task list → command list, D45) replaced by the C program (GEN2); the scenarios and `docs/CONTRACTS.md`. Decided in GVS4.

## M16: SNAX-GVSoC aligned with snax_cluster (D116)

SNAX-GVSoC is built by hand to match snax_cluster, and checked against its
RTL before anything is generated, so it is the baseline M14's generators are
accepted against. Work happens in the snax-gvsoc repository on the MICAS
server, and the RTL runs in a `snax_cluster` checkout on the author's side.
Each task is planned in its own round. A SNAX-GVSoC model is checked by
running the same ELF on both sides and comparing the counters that do not
depend on the core's timing (D123), a feature of the whole system that SG5's
regression, FLOW3 and GEN2 build on.

## Open Items

Questions not decided yet. Numbers are never reused; a closed item is
removed. Closed with D116: 5, 6, 7, 8 and 10 (SNAX-GVSoC follows
snax_cluster's RTL), 9 (into SG1, D120), 11 (into SG5), 14, 15 and 22 (SNAX-MODEL
details), 52 (the real program and cores do both), 55 (into
FLOW3). Closed in SG3: 59 (the streamer's cycle classes and queue counts)
and 61 (the crossbar's ports named by owner). Next free number: 65.

1. BRM dataflow notation: `affine` since D70, frozen in M6. A rank-free
   notation for unit BRMs comes earlier, with ND1 (open item 45).
2. What automated search reads and how a sweep is configured (DSE1, M8); a
   sweep is one recipe with a parameter (D72).
3. The error target between SNAX-GVSoC and snax_cluster RTL: three tiers,
   fixed in snax-gvsoc `SG5.md` (SG5 P1) before the first comparison, and
   logged in `docs/DECISIONS.md` when SG5 closes.
4. Stream as a proposer for DNN-shaped workloads, replayed as a recipe at
   cycle level, and an analytical estimator of our own for the kernels Stream
   cannot describe (the engine alone, open item 49, plus bank conflicts from
   the memory passes' address streams, D86). Parked (D23).
18. The L1 address map is fixed and word-interleaved, which is why the design
    point states no banks. If snax_cluster's map differs, it becomes a
    registered map kind.
20. Streamer ports are one bank wide; a wider port when a kernel needs it
    (PACK1).
21. `elems_per_word > 1` (packed words) has never been moved by streamers,
    accelerators or the DMA. Decided with sub-word packing (PACK1).
23. Data values on beat-level events, so the cluster view can show them.
    Decided with FLOW3's converter, together with open item 25.
25. No trace event for an accelerator's push into its output FIFO, so a push
    and a pop in one cycle show no arrow in the cluster view. Decided with
    FLOW3, together with open item 23.
27. Generating a BRM from Chisel, SystemVerilog or HLS sources instead of by
    hand. Far future.
28. Implementations whose `source` is SystemVerilog or HLS: only `chisel`
    until one is needed (E8).
31. A loop bound that is not a multiple of the spatial bound: `split_map`
    rejects it; a tail task or padding later.
32. The DFG viewer's layout (rows in Python, SVG edges, no library), revisited
    if graphs outgrow it.
33. An MLIR importer that writes `.snaxdfg` directly.
34. A hand-edited `.snaxdfg` runs through the flow (D108) but cannot be
    replayed or swept, and the design checks' fixes still speak of the
    recipe. Decided when needed.
36. Control flow in SNAX-DFG: a sequential `loop` kind for time steps and a
    `branch` kind with `case` nodes, registered when a kernel needs them (M9).
37. The expression grammar has `+ - * //` only: tail tiles need `min`,
    branches comparisons, jacobi1d a cast. Extended when a kernel needs it.
38. The DMA moves a container as contiguous whole beats (padded, D105);
    strided or 2-D transfers when a kernel needs them, with a check of the
    DMA's loop count.
39. Beat-trace size, about 1.1 KB per vecadd element; a more compact format
    when a run needs it. Measured again on SNAX-GVSoC (FLOW3).
40. Switching runs in the viewer clears the selected cycle; kept as is until
    a comparison needs it.
41. A report glossary, a "where the cycles went" ranking and a list of the
    knobs with their `--set` paths, on hold; a decision of its own when built.
44. Reductions over tiles need partial sums and a final combine; until then
    no tile loop sits around a `reduce` memlet. Decided with LOW3b.
45. A unit BRM's nest is one-dimensional, so 2-D containers and operands
    reused across an outer loop are rejected; a scratch run showed that with
    the checks relaxed, row and column sums, `A @ x` and `x @ A` run. Decided
    in ND1.
46. No transform tags an outer map `temporal` or `tile` without splitting
    it, and `bind` under an untagged map fails without a named error.
    Decided in ND1.
47. An in-place update (`y += x`) binds but does not lower: the writer waits
    for its own node's reader. Decided in LOW4.
48. The flow sizes inputs from one bound symbol, and fills take 1-D arrays
    only. Decided in ND1.
49. The engine-alone number C3 compares against (firings × II + latency) is
    computed nowhere; it belongs in `design.md` (DSE0).
50. Simulation speed: SNAX-MODEL ran about 4,000 cycles per second, so C1
    rests on turnaround and cause. Measured again on SNAX-GVSoC in BASE2;
    timing-only runs and extrapolation only if that is still too slow.
51. What snax_cluster has to change for a generated accelerator: a Bender
    dependency on the bundle (through `Bender.local`), a target listing the
    files `snaxgen` generates, later a file list `snaxgen` writes itself; the
    wrapper is named `<name>_shell_wrapper`. Settled in LNK2.
53. A link between two shell accelerators: amends D12 and D51 and the SNAX
    shell. Parked (D112).
54. Which kernels take PolyBench's SMALL in a 128 KiB L1, and the tolerance
    of the NumPy check for float sums. Decided in FE1a.
56. `gvrun` ends in `exec python3 -m gvrun`; inside a pixi task `python3` is
    pixi's Python, without GVSoC's packages (`/opt/venv` in the image). How
    the flow calls `gvrun` is decided in FLOW3.
57. SNAX-GVSoC's components trace for people (`vp::Trace` text). The views
    and reports need SNAX-MODEL's events (C§7: task and beat levels, the
    source and window filters of D49, a `fifo` event at the first cycle its
    count holds) and its profile counters written at the end (D38). A
    shared event writer in snax-gvsoc that writes them would leave FLOW3's
    converter almost nothing to do. Decided with FLOW3.
58. The cores and the DMA reach the TCDM banks outside the SNAX crossbar
    (D122): their accesses and their clashes with streamers are not in its
    events, and a clash costs the later access one cycle instead of a
    round-robin stall. Events from the bank memories, or the cores in the
    crossbar, when a program's numbers need it (SG5 or later).
60. `cmd` and `poll` events with the pc, and the controller's cycle
    classes (`command`, `wait`), from the Snitch core's SNAX CSR path (an
    upstream file in snax-gvsoc). Decided with FLOW3.
62. SNAX CSRs differ from Zicsr on both sides. On the RTL a SNAX `csrrw` /
    `csrrwi` with `rd` not `x0` writes without reading and gives `rd` the
    ALU's sum of `rs1` (or the immediate) and the CSR number, and `csrrs` /
    `csrrc` only read. GVSoC's ISS (`priv.hpp`, every core) writes on
    `csrrc` with `x0` and on `csrrsi` / `csrrci` with 0. No SNAX program uses
    these forms; SNAX-GVSoC warns on them since SG4. Fixed in SG6.
63. A common start and busy protocol for all accelerators. Today they differ:
    the ALU (`snax_alu_csr.sv`) never holds a start, also while busy, keeps
    `len_counter` across a start, lets the end win over a start in the same
    cycle, and never ends with length 0; the streamer holds a start while
    busy, which SNAX-GVSoC refuses with a warning. The protocol, and the
    snax_cluster changes it needs (`snax_alu_csr.sv`, the ReqRspManager's
    `ready`), are formalized with GEN1 and GEN3.
64. Accelerators made from BRMs need not take their data as the ALU does
    (both inputs and room for the output in one cycle): the interface
    towards the data may need modelling more generally, with hooks for how
    an accelerator waits for its data. Taken up with GEN3, starting from the
    ALU's `try_fire` and `compute` in snax-gvsoc.
